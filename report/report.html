Failure 1: "ping me" → wrong action (test-030, 043, 058)

test-030: "Ping me the day after tomorrow at 5:30pm so I remember to order a birthday cake." Expected set_reminder, predicted schedule_meeting; all other fields were right.

  • Happened on all 3 "ping me" test sentences, so it is systematic, not random.
  • In training, all 129 reminder sentences had the word "remind" or "reminder", and no sentence had "ping". The model learned "remind = reminder" as a keyword shortcut instead of the meaning; with no trigger word, it fell back to schedule_meeting.
  • Fix: more varied ways of asking for each action (e.g. paraphrase the training data with a bigger LLM).

Failure 2: date maths (test-033, test-036)

test-033 (seen template): "Set a reminder to send the invoice to Acme at 6:30pm in 12 days." Expected 2026-12-02, predicted 2026-12-01: crossing into a new month broke it. test-036: "on Monday" → 2026-11-22, which is a Sunday; correct is 2026-11-23.

  • test-033 uses a SEEN template, so this is a reasoning weakness, not a phrasing problem. The model doesn't actually calculate dates; it just predicts likely-looking date tokens.
  • Fix: let the model output the relative phrase ("+12 days", "next Monday") and calculate the real date in Python with datetime.

Failure 3: subject-first sentence (test-052, test-034)

test-052: "The design review with Sneha in 4 days is not happening anymore, please remove it." Expected title "design review", attendees ["Sneha"]; predicted "the design review" (extra "the"), attendees []. test-034 (same pattern): the same title error, and the date "today" came out null.

  • In all training sentences the meeting comes after the verb ("Cancel the X..."), so the model learned to find fields by their position after the verb. When the meeting is the subject of the sentence, that breaks.
  • This shows the fine-tune overfit a bit to the typical phrasing patterns. It needs more varied sentence structures in training.

  • Why 16 B for full FT: mixed precision runs the maths in 16-bit (2 B weights, 2 B gradients). The optimizer still updates an fp32 master copy (4 B), because tiny updates would vanish in fp16. AdamW also keeps two fp32 running averages per weight (8 B).
  • Why ~0.52 B for QLoRA: NF4 stores 4 bits = 0.5 B per weight. Each block of 64 weights also stores one scale; with double quantisation that costs 8/64 + 32/(64·256) ≈ 0.127 bits ≈ 0.016 B per parameter, so the total is ≈ 0.5 + 0.016 ≈ 0.516 B.

Step 2 — LoRA adapters: r·(din + dout) = 16 × (4096 + 4096) = 131,072 per matrix; × 4 matrices (q, k, v, o) = 524,288 per layer; × 32 layers = 16,777,216 ≈ 16.8M trainable parameters (≈ 0.24 % of 7,000M). With AdamW: 16,777,216 × 16 B = 268,435,456 B ≈ 0.27 GB.

Step 4 — Activations (Korthikanti et al., 2022): per layer ≈ s·b·h·(34 + 5·a·s/h) bytes. LoRA and QLoRA still need almost all of them: the gradient for an adapter in layer 1 has to flow back through all 32 frozen layers.

  • 34·s·b·h = 34 × 2048 × 1 × 4096 = 285,212,672 B ≈ 0.285 GB per layer (inputs of the projections, the MLP and the norms).
  • 5·a·s²·b = 5 × 32 × 2048² × 1 = 671,088,640 B ≈ 0.67 GB per layer (the stored s × s attention scores; FlashAttention / PyTorch SDPA do not store this matrix).

Why 150 beat 500

  • The biggest reason is truncation: MiniLM caps out at 256 tokens (~190 words), so anything later in a 500-word chunk gets cut off and never embedded. That's why Q6 (bias) missed at 500, even though it was rank 1 at 150.
  • Big chunks also dilute the meaning by squishing multiple topics into one averaged vector.
  • The 60% word-overlap hit rule actually gives 500-word chunks an advantage (a bigger chunk is more likely to contain the passage), and 150 still won.

Failure 1: Q10 "When should you pull the plug on building or using an AI system?" (both sizes)

Source: page 13, "… development and deployment should cease in a safe manner until risks can be sufficiently managed." Retrieved, 150 words: p. 6, pp. 42–43, p. 24, p. 19, pp. 46–47; 500 words: pp. 6–7, pp. 46–48, pp. 30–31, pp. 4–6, pp. 7–8. No chunk from page 13.

  • "Pull the plug" is an idiom and shares no words with the actual text ("cease", "unacceptable negative risk"), so the small embedding model didn't connect them and grabbed generic "AI system" chunks from p. 6.
  • BM25 wouldn't fix this, since there's no keyword overlap to match. Better fixes: LLM query rewriting / HyDE to turn casual phrasing into the document's language first, a stronger embedding model (bge/e5), or a re-ranker on the top 20.

Failure 2: Q7 "What is the MAP function supposed to do?" (150 words)

Source: page 29, "The MAP function establishes the context to frame risks related to an AI system." Retrieved, 150 words: p. 46, pp. 29–30, pp. 30–31, p. 30, p. 32. With 500-word chunks it was not a miss.

  • "MAP" shows up all over the document, so the embedding model couldn't tell the main definition on p. 29 apart from chunks about GOVERN or later MAP sections.
  • The flip side of Q10: hybrid search with BM25 would help here, by boosting exact matches like "MAP function" together with defining words. A re-ranker would also help pick out the actual definition.

BM25 and re-rankers

  • BM25 scores chunks by exact word matches, giving extra weight to rare/specific terms and penalising very long chunks. Embeddings are good at general meaning but get fuzzy on exact names, codes and acronyms (like MAP). Combining both is hybrid search: meaning plus exact matches.
  • Re-ranker: two stages. First, fast search pulls a wider shortlist (the top 20–50 chunks); then a cross-encoder reads the question and each chunk together and scores how well that chunk actually answers the question. This is much more accurate than comparing two separate vectors, but slower, so it only runs on the shortlist.

  • The biggest drop was the creative poem: fp16 kept the 4-line limit, but q4_K_M wrote 12 lines with repeated lines.

  • Shared 1.5B limits: both said Canberra but gave a wrong reason ("centre of the country"), both got cut off on the bat-and-ball problem, and both made grammar mistakes in the French.

KV cache

  • When an LLM generates text one token at a time, attention has to look back at every previous token. The KV cache stores the Key and Value tensors for all the tokens already processed, so the model doesn't recompute them for every new token. It trades extra memory for much faster generation.
  • It grows with context length and with the number of users at the same time. That's what limits serving.

Quantisation

  • Weights are normally 16-bit floats (2 bytes per parameter). Shrinking them to 8-bit or 4-bit cuts memory by roughly 2x to 4x. My run: memory 3.28 → 1.17 GB (2.8x), generation 12.3 → 28.1 tok/s (2.3x).
  • It's 2.8x and not 4x because q4_K_M uses ~4.5–5 bits per weight and keeps some parts at higher precision, and the measured size also includes the KV cache and buffers.
  • It's faster because each new token means reading all the weights from RAM (this ran on CPU), and smaller weights = less data to read per token. Usually there is only a small hit to quality.
